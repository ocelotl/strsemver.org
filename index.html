Strict Semantic Versioning

An improved variant of Semantic Versioning.

Strict Semantic Versioning is a new and improved version of Semantic Versioning. This project is hosted at the strsemver.org domain.

Semantic Versioning is incomplete. It lacks definitions for two critical concepts:

  1. Public API
  2. Breaking change

Strict Semantic Versioning includes definitions for those two concepts (and more).

Definitions of the two missing concepts

Public API. A public API is a set of symbols from a software library.

Breaking change. A breaking change is the removal of a symbol from the public API.

Worked example

Consider this library:

class A:
    method x(p, q)

Then the public API consists of two symbols:

  1. class A
  2. class A / method x(p, q)

A non-breaking change is the addition of a symbol to the public API:

1. class A
2. class A / method x(p, q)
3. function g(i, j)

A breaking change is the removal of a symbol from the public API. After removing class A and its method, the public API is: 

1. function g(i, j)

Precise meaning of the version numbers

With these definitions, the MAJOR, MINOR, and PATCH numbers now have a precise, deterministic meaning:

  • MAJOR: increased when there is a breaking change.
  • MINOR: increased when there is a non-breaking change.
  • PATCH: increased when there is any other change.

This means a library that uses Strict Semantic Versioning MUST declare its public API.

The subjectivity of breaking changes

Unfortunately, the term "breaking change" is used nowadays to refer to any change that can produce undesired behavior for the end user of the library. There is something important that needs to be stated: any change to a library can cause undesired behavior for the end user of the library. End users must be aware of this.

Version numbers are not only an identifier of a particular state of a software library. Version numbers are also a message to the end user. A version number can carry this message to the end user: be careful and test this version before you put it into production.

That is fine, but it should not be bundled up with the increase of the MAJOR number. This is why Strict Semantic Versioning separates the strictly defined idea of a breaking change from the subjective idea of undesired behavior for the end user.

The trailing exclamation mark

A strict semantic version number consists of these fields:

MAJOR.MINOR.PATCH!

Notice the ! at the end. That ! means: this version can cause undesired behavior for the end user; the end user must read the changelog and test this version before putting it into production.

Every strict semantic version number ends with !, because every change to a library can cause undesired behavior for the end user.

The changelog

Another critical artifact is the changelog. The changelog is the artifact library developers use to communicate with the end users.

If the library developers consider that a particular change in a new version is likely to cause undesired behavior for the end user, then they SHOULD add a message in the changelog, prefixed with the word WARNING, where that change is explained. The library developers MUST NOT describe that change as a breaking change unless it is actually a breaking change per the definitions above.
